## 二、项目介绍

### 1. 游戏规则

棋盘的每个格子为空，或者放置一支朝上、下、左、右的箭头。玩家用鼠标左键点击箭头后，程序从箭头前方的相邻格开始，沿其方向一直检查到棋盘边界。

- 路径上没有其他箭头：播放飞出动画，随后消除该箭头。
- 路径上存在其他箭头：箭头保留在原位，播放碰撞反馈，并扣除一次失误机会。
- 阻挡者的方向不影响判断，两个箭头之间即使隔着空格也仍然会阻挡。
- 点击空格、棋盘外、已消除的位置或使用右键，不会改变棋盘，也不会扣除次数。
- 清空本关全部箭头后通关；3 次机会用完后失败，可以重新开始本关。

动画期间只接收一个棋盘动作，防止重复点击造成一次删除多个箭头或连续扣除机会。重开、静音和关闭窗口仍然可以使用。

### 2. 固定关卡

作业要求至少 3 个可通关关卡，我设计了 6 个固定关卡，难度按棋盘大小、箭头数量和阻挡关系逐步增加。每一关都含有四种方向。

| 关卡 | 名称 | 棋盘大小 | 箭头数 | 三星目标时间 | 设计重点 |
|---|---|---:|---:|---:|---|
| 1 | 初识箭序 | 5×5 | 9 | 45 秒 | 边缘飞出与简单阻挡 |
| 2 | 留意空隙 | 5×5 | 12 | 55 秒 | 隔着空格也会阻挡 |
| 3 | 交错之间 | 6×6 | 19 | 75 秒 | 横向和纵向依赖交错 |
| 4 | 逐一解锁 | 6×6 | 23 | 85 秒 | 连续解除多层阻挡 |
| 5 | 四向交织 | 7×7 | 31 | 110 秒 | 更长的路径与更高密度 |
| 6 | 最后之序 | 7×7 | 36 | 125 秒 | 综合四方向判断 |

关卡模板不会在游戏过程中被修改。开始和重开时，程序重新复制一份棋盘，因此不会出现重玩后布局缺失的问题。

### 3. 附加功能

完成基础玩法后，我加入了几项附加功能：

- 每次挑战有 3 次提示，提示会高亮一个当前可以飞出的箭头，但不会替玩家点击。
- 关卡逐关解锁，并将最好成绩、星级和音乐设置保存到本地。
- 通关至少获得 1 星；剩余 2 次及以上机会再得 1 星；在目标时间内完成再得 1 星。
- 音效和背景音乐可以分别关闭。背景音乐与操作音效由项目代码合成，没有使用商业游戏素材。
- 无尽模式会随机生成 5×5 至 7×7 的可解棋盘，不改变普通关卡进度。
- 程序已使用 PyInstaller 打包为 Windows EXE，运行时不需要安装 Python，也不需要联网。

## 三、实现思路

### 1. 项目结构

我没有把所有内容写在一个文件里，而是把规则、关卡、计分、随机生成和界面流程分开：

```text
game.py                  游戏状态、事件循环、绘制、动画和音频
arrowgame/rules.py       路径检测、消除与求解
arrowgame/levels.py      六个固定关卡
arrowgame/scoring.py     计时、星级和最好成绩
arrowgame/endless.py     随机可解关卡生成
tests/                   规则、流程、计分和无尽模式测试
```

其中 `rules.py` 不依赖 Pygame，可以直接用普通二维数据测试。这样在界面发生变化时，核心规则仍然能单独验证。

### 2. 箭头、方向和关卡的表示

棋盘用二维网格表示，`.` 是空格，`U/D/L/R` 分别表示上、下、左、右。四个方向统一映射为行列增量：

```python
DIRECTIONS = {
    "U": (-1, 0),
    "D": (1, 0),
    "L": (0, -1),
    "R": (0, 1),
}
```

例如第一关的关卡模板是：

```python
(
    "U.U.U",
    ".....",
    "L.U.R",
    ".....",
    "D.D.D",
)
```

关卡数据保存在不可变的字符串元组中，真正开始游戏时调用 `fresh_board()` 转成列表。消除箭头只修改这份运行中的副本。

### 3. 路径检测

路径判断的重点是从“箭头前方的下一格”开始检查，而不是从箭头本身开始；循环时先判断坐标是否仍在棋盘内，再读取格子。这样可以避免 Python 负索引把上边界错误地读成最后一行。

```python
def first_blocker(board, row, col):
    for r, c in path_cells(board, row, col):
        if board[r][c] not in EMPTY:
            return r, c
    return None


def can_exit(board, row, col):
    rows, cols = _shape(board)
    if not (0 <= row < rows and 0 <= col < cols):
        return False
    if board[row][col] in EMPTY:
        return False
    return first_blocker(board, row, col) is None
```

`path_cells()` 根据方向增量逐格前进，直到离开边界。只要路径上遇到一个非空格，`first_blocker()` 就返回最近阻挡者；一路没有遇到箭头时，`can_exit()` 才返回 `True`。一次判断只扫描一行或一列，时间复杂度为 `O(max(行数, 列数))`，额外空间为路径长度；当前棋盘最大为 7×7，这部分开销很小。

### 4. 关卡可解性

固定关卡在加载时会检查棋盘是否为矩形、是否包含四种方向，并运行求解器。求解器找到当前能飞出的箭头，尝试删除后继续搜索；所有箭头都能删除时返回完整顺序，找不到合法动作则判定无解。

```python
def solve_order(board):
    initial = tuple(tuple(row) for row in board)

    @lru_cache(maxsize=None)
    def search(state):
        if count_arrows(state) == 0:
            return ()
        for row, col in available_arrows(state):
            rest = search(remove_arrow(state, row, col))
            if rest is not None:
                return ((row, col),) + rest
        return None

    return search(initial)
```

这里使用带缓存的深度优先搜索，既能给出可解结论，也能保存一条合法通关顺序。求解器只用于开发验证和提示选择，普通游戏界面没有“一键通关”按钮。

无尽模式采用反向插入方式生成棋盘：每次只把新箭头放在当时可以飞出的位置，因此反向删除时一定存在合法顺序。程序还会检查箭头数量、四种方向和依赖深度；随机尝试没有在限定次数内得到合适布局时，会对已验证的固定关卡做旋转或镜像作为保底。

### 5. 动画和状态切换

程序区分首页、选关、游戏、飞出动画、碰撞反馈、单关通关、失败、全部完成、无尽结算等状态。同一时刻只处理一个棋盘动作。

飞出动画约 0.3 秒，动画结束时才真正删除格子。碰撞先扣除一次机会，再播放前冲回弹和变色；最后一次碰撞反馈结束后才进入失败页。所有动画都按经过时间推进，没有使用 `sleep()` 阻塞主循环，所以窗口在动画中仍能关闭或重开。

重开会清空旧动画并重新复制关卡模板。结果页出现后，按钮区域会重新生成，底层棋盘不再接收点击。

## 七、心得体会

这次作业里，AIGC 最直接的帮助是把需求、实现和测试连在了一起。我一开始给出的不只是“做一个箭头游戏”，还确认了每关次数、动画期间如何处理点击、重开要恢复什么、最后一关结束后去哪里。规则写清楚以后，后面的代码和测试才有统一标准。

开发过程中也出现过需要继续检查的问题。第一版预览的中文字体太细，棋盘附近的间距和状态数字不够统一；我提出配色不能照着参考博客做，界面随后改成现在的雾蓝紫方案。后续功能增加后，测试第一次在受限临时目录中运行还遇到了权限错误。换到正常 Windows 临时目录重新执行后，26 项 `unittest` 才完整通过；纯规则测试又单独运行了 7 项。这个过程提醒我，命令报错不等于代码一定有错，应该先区分运行环境问题和程序断言失败。

我对核心实现的理解是：方向映射决定箭头每一步的行列变化，路径检测只查看箭头前方同一行或同一列；关卡模板必须复制后再修改；动画状态负责保证一次点击只产生一次结果；存档只保存已解锁关卡和成绩，不保存未完成棋盘。求解器能验证关卡存在合法顺序，但不能代替我亲自玩一遍，因为操作手感、文字是否容易读、关卡是否太难都不是“可解”两个字能说明的。

目前源码、README、资源、测试和 Windows 程序已经准备好。发布博客前，我还需要完成六关上机试玩，补上真实感受、录屏链接和本人学号，并确认自己可以解释路径判断、动画状态和关卡生成代码。
